# Animal Crossing: New Horizons (01006F8002326000)

**State:** version 3.0.3 (+3 DLC) boots through the whole opening (Timmy's dialogue, the Nook Inc. counter, the name-entry keyboard) and shows its picture through the game's own window pass (2026-10-26: `nvnProgramSetShaders` with pool-offset code addresses is accepted, see the [gfx-correctness note](../archive/changes/2026-10-26-gfx-correctness-2026-10-26-macos1.md); the stopgap present is gone; Timmy and Tommy and other skinned meshes appeared once the translator read Maxwell LDC's signed immediate offset correctly); v0 (1.0.0) boots without crashes.

## What it needs
- NVN SDK 55.15 over TIPC for `sm`: refusal replies must carry the success layout with move handle 0 ([symptoms](../symptoms.md)).
- HID shared memory with even outer sampling numbers (outer = 2n).
- `IApplicationFunctions` cmd 210 event copy handle; a real clock (AdjustableUserSystemClock); `olsc:u` cmd 13; `prepo:u` 10104/10105; `SignalToAddress` type 2 value 2 and `WaitForAddress` type 3; VMNMX in the shader translator; conditional rendering evaluated at replay; command-buffer recording under one lock.
- About 19 000 tiny pre-recorded command lists at boot before the first submit.
- Acquire/release ordering on exclusive pairs in the rewriter (see "Start flake" below); title data built before that change must be rebuilt.

## What is open
- iOS Simulator: 100 s, no crash, no first frame.
- v0 was not re-run after the clock/olsc/prepo/pool-race changes (its data was deleted).
- Thread 0x56 is created but never started in every boot (harmless).

## Start flake (command-buffer race)
Headless starts failed about 10-30% of the time on the base build and about 5% on the update build (host SIGSEGV/SIGTRAP/abort in the gfx command recorder; also a guest null read at `main+0x1b61xxx`, and on the update build a guest Break at `sdk+0xc80730` after "program hash 0x3 is not a shader hash").
- Cause ([gfx-recorder-flake](../archive/changes/2026-10-28-gfx-recorder-flake-2026-10-28-b8.md)): two guest threads record the same object's command list at once (`main+0x1ae75c0` binds a stack-allocated context into a shared per-object slot). One thread then works on the other's stack-allocated `NVNcommandBuffer` while its owner finalizes, re-initialises and finally overwrites it. The old recorder turned that into a use after free, `realloc` races and a 64-byte static scratch overflowed by large commands.
- Fixed in gfx: host parts are addressed by slot+generation and never freed; the recording state is locked; grown buffers are freed late; unrecorded commands go to a payload-sized sink. `gfx/tests/t_cmdshare.c` reproduces the misuse without a game. After the gfx fix: update+DLC 0 of 40, both builds 0 of 10 under MallocScribble, base 3 of 40, all three guest null reads (`main+0x1b61d3c`, `main+0x19d04d4`, `main+0x667178`) with no recorder warning and no host heap crash. Find overlaps with `NAPPLE_GFX_CBTRACE=1`, which dumps both threads' events and backtraces.
- Not a scheduling bug ([sched-applets](../archive/changes/2026-11-01-sched-applets-2026-11-01-r1.md)): two real Horizon divergences were fixed (equal-priority rotation only at priority 59; a preempted thread keeps the head of its priority), but the base build overlapped as often as before (30 s starts with `NAPPLE_GFX_CBTRACE=1`: 8 of 20 runs before, 11 of 40 after) and also with `NAPPLE_SLICE_MS=0` (2 of 10): timer preemption is not the trigger.
- The collision is always the guest main thread 0x51 (core 0) against worker 0x57/0x58 inside the same parallel-for job path (dispatcher `main+0x19b7460`, item method `0x19b654c`, view method G `0x1ad9018`, recorder F `0x1ae75c0`); job pop and item claim are spinlocks. The job manager's own "wait for workers" (`0x19b6ed0`) is compiled to discarded loads and does not wait (same shape in the update at `0x390d2b0`).
- **Fixed** ([acnh-race-atomics](../archive/changes/2026-11-01-acnh-race-atomics-2026-11-01-r3.md)): the job's item-claim spinlock (`main+0x19b65d4`) acquires with plain `ldxr/stxr`; Apple cores run the protected loads early, so two threads claimed the same items (litmus on an Apple-silicon Mac: thousands of double claims per 41 M with `ldxr`, 0 with `ldaxr`). The rewriter now gives every exclusive pair acquire/release ordering; title data must be rebuilt. The kernel sync path (LightEvent / MessageQueue svcs) was traced at a real collision and is correct. Open: the AArch32 lifter still emits plain `ldxr/stxr` for `ldrex/strex` (tracked in [open work](../todo.md)).

## Bring-up notes
- The 3.0.x SDK uses TIPC for `sm`. Boot blockers that show the typical "blocker -> one service fix -> symptom row" path: the TIPC `sm` refusal reply (must keep the success layout with move handle 0, otherwise "request on handle 0") and `IApplicationFunctions` cmd 210 (a copy handle to an event, not an object; otherwise a spin on `WaitSynchronization(handle 0) -> 0xe401`) ([ac-boot-spin](../archive/changes/2026-10-24-ac-boot-spin.md), [guest-handle](../archive/changes/2026-10-24-guest-handle.md)).
- Address arbiter: needs `SignalToAddress` type 2 writing `value-2` and `WaitForAddress` type 3 ([ac-render](../archive/changes/2026-10-25-ac-render-2026-10-25-titles.md), item 8).
- Frames 0 with a spin found by `NAPPLE_PCPROF=1`: the Npad reader at `sdk+0x5087xx` (HID outer sampling numbers).
- The command-buffer race was found by repeating the same headless boot.
- `NAPPLE_NO_ORPHAN=1` disabled the stopgap present pick that this title used before its own window pass was accepted.

## Graphics
- NVN SDK 20.5.4. Its NVNprogram is allocated 0x80 bytes and followed by an NVNbuffer at +0x80 (a program at 0x7037b845c0 still carried its magic when the game set up an NVNbuffer at +0x80 and a memory pool at +0xb0, suggesting {NVNprogram 0x80; NVNbuffer 0x30; NVNmemoryPool}). A host program layout that zeroed +0x80..0x88 at Initialize / SetShaders overwrote that buffer and produced "program hash 0x3 is not a shader hash" (fixed in 30e67b4; `NVN_MIN` of NVNprogram is 0x80 because of this title; table in the [title notes](README.md#graphics-measurements)).
- The window pass calls `nvnProgramSetShaders` with bare shader-code pool offsets as code addresses; they are accepted and resolved at the first draw (`NAPPLE_PROGRAM_POOL_OFFSETS=0` restores the old rejection, after which the title never binds those programs).
- A shader binds a 15x15 R8 texture (2.5 KiB) as a cube map; served as a copy-backed cube with the image on every face.
- A pass into a mip level made Metal's validation abort until every scissor was clamped to the render pass size.
- `VMNMX` was first found here: fragment shader `23e43e94e45bb1d5` at 0x3e8 holds `0x3b34056060470100` (the worked example in [add-maxwell-shader-op.md](../guides/add-maxwell-shader-op.md)).
- Two guest threads can record into the same command buffer; null and finalized buffers once crashed one run in three before the recorder tolerated them (see "Start flake").
- Sets `NVN_TEXTURE_FLAGS_IMAGE` on every screen-sized render target.
- Geometry programs (3.0.3 + 3 DLC): 8 distinct (triangle strip, 6 output vertices) in `Swkbd/shader/*OceanShader*` (the game's own keyboard; NX and Win variants); 2 are created at boot, and the name-entry keyboard does not bind them. The 2 boot-time programs run through the geometry stage with finite output in `t_stages_dumped`.
- Shader corpus (base + updates + DLC): 8,577 programs, all translate and compile with Metal.
- Golden-frame route: the airport counter. Routes still to add: name entry, island arrival.
- Headless boot with `MTL_DEBUG_LAYER=1`: 90 s, exit 0, 0 unimplemented NVN calls, no validation message.
